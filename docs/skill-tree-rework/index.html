Zombie Blaster · design proposal · warrior first

Skill tree rework

One skill point per level. Each skill costs one point and has no levels. Your stats decide how strong a skill is. You fire skills with moves you already know (tap, hold, direction plus attack, double-tap), not with skill keys 1 to 6.

Update, 2026-10-11: the gesture input below was built, played and dropped. It felt messy: skills mixed with each other and with plain attacks. Actives and buffs now fire from a skill bar: keys 1 to 6, one key per skill. Learning a skill puts it on the first free key, and the tree window moves it to another key. Passives work by themselves. The rest of this report (points, stat scaling, branches, skills) still holds.

1 level = 1 pointEvery level up gives exactly one point. A full warrior tree is 22 nodes, so build choices matter all game.

1What we have today

Skills

  • One flat SKILLS array in shared/game-constants.ts. Each skill has 5 to 30 levels with levelData tables.
  • 3 skill points per level (SKILL_POINTS_PER_LEVEL). Players put points into levels of the same skill.
  • Warrior has 9 skills: Power Strike, Slash Blast, Power Dash, Monster Magnet, Dragon Roar, Power Stance, Hyper Body, Improved HP Recovery and Auto Potion. Assassin has 6. Ranger, Mage and Priest only have Auto Potion.

Firing a skill

  • Keys 1 to 6 map to slots by position: learned skills sorted by required level. Learning a skill can move every key.
  • Holding attack re-swings every cooldown. Nothing reads hold, charge or double-tap.
  • The HUD skill bar shows no cooldown (TODO.md asks for icon and cooldown only).
  • Skills, XP and skill levels live only on the client. The server never checks them.
Problems this fixes. The playtest notes say skills arrive late and feel weak, and bots spent every point on Auto Potion. Keys change meaning as you learn skills. Having levels and stats means two number systems to balance, and players end up maxing one skill instead of making choices.

2Core rules

Points and unlocking

  1. 1 point per level, including the first: a level 1 character has 1 point. Points never expire.
  2. Every node costs 1 point and is either owned or not.
  3. A node unlocks when (a) your level reaches its tier level and (b) you own at least one node it links from. Tier 1 nodes have no parent.
  4. Tier levels: T1 lv 1 · T2 lv 4 · T3 lv 8 · T4 lv 12 · T5 (capstone) lv 16.
  5. Warrior: 22 nodes in 3 branches. You own all of them at level 22, so up to about level 15 you have to choose.
  6. Respec at the safe spot between floors. The first one is free, then RESPEC_GOLD_PER_LEVEL × level gold.

Strength from stats, not points

  1. Damage is ATK × multiplier, and each skill has a fixed multiplier.
  2. Each skill's secondary values (reach, radius, duration, cooldown, chance) are a soft-capped curve of one stat: min + (max − min) × s / (s + half).
  3. STR drives power, radius and knockback. DEX drives distance, speed, cooldown and timing windows. LUK drives chance and crits. Max HP drives heal amounts.
  4. The 5 stat points per level stay. They are now the only way to make a skill stronger.
  5. Every number lives in shared/game-constants.ts (SKILL_TREE_WARRIOR, GESTURE_*).
Input rules.
  1. Every skill is a gesture made from the keys you already use: Move, Up, Down, Jump and Attack.
  2. A gesture slot holds at most one skill per class, so moves never clash.
  3. No dead inputs: if a gesture's skill is not owned, is on cooldown or lacks MP, it does the normal thing (basic swing, jump, walk).
  4. Context comes first: interact, then ladder or rope, then carrying a corpse, then gesture. Holding Up next to a ladder climbs; it does not cast Hyper Body.
  5. Every gesture works the same on keyboard, mouse, gamepad and (later) touch.

3The gesture system

The engine sees six inputs: ←→↑↓SpaceJ. The new GestureReader turns key press and release times into gestures. Each gesture has a type (tap, hold-release, double-tap, timed), a direction (read when attack is pressed) and a context (on the ground, in the air, sprinting, standing still, being hit).

Timing: tap versus hold on the attack key

  • Pressing attack starts a basic swing at once. Taps feel the same as now. The swing hits at 360 ms.
  • If you are still holding at 180 ms (GESTURE_HOLD_MS) and you own a hold skill for that direction, the swing cancels into a charge pose. Charge pips show above your head and other players see them too.
  • Charge stages at 300 / 650 / 1000 ms (GESTURE_CHARGE_STAGES_MS) set how far the dash goes or how wide the roar reaches. Release fires the skill. Holding past 2000 ms fires it at full power.
  • If you don't own a hold skill, holding attack keeps auto-swinging as it does today.
  • Accessibility settings: hold threshold 150 to 300 ms, and a toggle charge mode (press once to charge, again to release).

  • Power Strike at T1 and Power Dash at T1 mean there's an attack skill at level 1, as the playtest asked.
  • Capstones (Dragon Roar, Rampage, Last Stand) need level 16 and a T4 node, so each one takes a commitment to its branch.

7Stat scaling model

One formula for every secondary value

// shared/skill-tree.ts
export interface StatCurve {
  readonly stat: ScalingStat; // 'str' | 'dex' | 'luk' | 'int' | 'atk' | 'maxHp'
  readonly min: number;       // value at stat 0
  readonly max: number;       // asymptote, never reached
  readonly half: number;      // stat that gives the halfway value
}
export function curveValue(c: StatCurve, s: number): number {
  return c.min + (c.max - c.min) * (s / (s + c.half));
}
  • Diminishing returns are built in, so no stat value can break a skill (dash length can't pass the edge of the screen).
  • Damage stays linear: ATK × mult, and ATK already grows with STR.
  • One shared helper replaces the per-level levelData tables (about 900 lines of game constants).

Power Dash distance against DEX

Dash = 160 + 160 × DEX / (DEX + 40), then × 0.5 / 0.75 / 1.0 for charge stages 1 to 3. The first 40 DEX gives half the bonus. The curve flattens towards 320 px.

8HUD, discoverability and onboarding

Mock: the skill bar is gone. A cooldown row under the portrait shows only owned active skills with a cooldown, as icon plus shrinking shade. A charge meter floats over the player. A "New move" toast appears when a skill is learned.

How players learn the moves

  1. New move toast (6 s): icon, name and keycaps such as ↑+J. It is the same component as the floor sign.
  2. Practice dummy at the safe spot: a training zombie that can't die. The first time you use the new move on it, you get "Nice" and a small XP tip.
  3. Move list (O then the Moves tab, or the pause menu): every owned gesture with its looping demo. This replaces "How to play → Skills".
  4. Hold hints: while you charge, faint labels for the possible releases appear next to the pips ("release: dash" / "↓ release: roar").
  5. Quick slots stay for potions and items only. Keys 1 to 6 are freed; we could later give them to items.

Settings

  • Hold threshold (150 to 300 ms), toggle charge, double-tap window, and "show move hints".
  • Rebinding stays per action (Attack, Jump, Up, ...). Gestures follow the bindings automatically.
  • Gamepad later: X = attack, A = jump, stick = direction. Same gestures, nothing new to map.

Multiplayer

  • Gestures resolve on the client that owns the player (input is local). Damage still goes as zombie-damage requests to the host.
  • New request: zombie-effect {zombieId, kind: 'launch' | 'knockdown' | 'stun' | 'knockback', skillId, dir}. The host applies it with values it computes from its own constants, so guests never move zombies directly. The existing magnet pendingPullEvents folds into this.
  • Charge is visible to everyone: player-state carries charge: {slot, startedAt} | null. Remote clients draw the pose and pips. Release sends a SkillAnimation VfxEvent (new keys: uppercut, ground-slam, shoulder-charge, backstep, leap-strike, parry, rampage-chain, last-stand).
  • Server validation (new): a skill-learned {skillId} message. The server checks the id is in the player's class tree, that owned count ≤ level, and that a parent is owned. zombie-effect from a skill the player doesn't own is dropped and rate-limited by the skill's cooldown.
  • Hyper Body and Rally touch allies. They go as ally-buff {targetIds, skillId}; each receiver applies the buff to itself (it owns its own player).

Save migration

  • Old skillLevels with level ≥ 1 become owned. Then skillPoints = level − owned. If that's negative, refund everything and show a free-respec toast.
  • Quick slots that hold skill entries are cleared, with a toast pointing to the move list.

11Claude flows for future classes

Proposed repo files, so a future session can design and ship a class tree the same way every time. They follow the existing pattern (stage-puzzle skill plus backlog, rules in .claude/rules/).

a. New rule file: .claude/rules/skills.md

# Skills and the skill tree

- One skill point per level (`SKILL_POINTS_PER_LEVEL = 1`). A node costs 1 point and has no levels.
  Never add per-skill levels, ranks or `levelData` tables.
- Skill strength comes from stats only: `damageMult × ATK` plus `StatCurve`s
  (`curveValue`, shared/skill-tree.ts). Every curve and multiplier lives in
  `shared/game-constants.ts` under `SKILL_TREE_<CLASS>`.
- Skills fire through gestures (`GestureSlot`), never through a dedicated key. One skill per slot per
  class; `skill-resolver.spec.ts` enforces it.
- No dead inputs: an unowned, cooling-down or unaffordable gesture falls back to the base action.
- Context priority: interact > ladder/rope > carry > gesture.
- Every gesture must work with keyboard, mouse and gamepad; timing windows read `GESTURE_*` constants
  and respect the hold-threshold / toggle-charge settings.
- Host authority: guests send `zombie-damage` / `zombie-effect` requests; the host computes the effect.
  Charge state rides in `player-state`; every cast pushes a `VfxEvent` (multiplayer-vfx-sync skill).
- Server checks `skill-learned` (class tree, count ≤ level, parent owned) and drops effects from
  unowned skills.
- Every node ships with: icon (pixel-icons), animation entry, a gesture e2e spec (solo) and an
  online visibility check, and a row in the class's move list.

# Class skill tree

Reference implementation: the warrior tree (`SKILL_TREE_WARRIOR`). Backlog: `docs/skill-ideas.md`.

## Flow
1. **Identity**: 3 branches, one sentence each (offense / mobility-control / survival-co-op works
   for most classes). Pick branch colours from tokens.css.
2. **Slot map**: fill the GestureSlot table (docs/skill-ideas.md has one per class). Each slot holds at
   most one node. Leave slots empty rather than force a skill in. Write down the fallback per slot.
3. **Nodes**: 20-24 nodes, tiers 1-5 at `SKILL_TIER_LEVELS`, 1-2 roots per branch, one capstone per
   branch at tier 5 with a tier-4 parent. Reuse existing skills where they fit.
4. **Numbers**: `damageMult` + `StatCurve`s against the class's primary stat. Fill the
   balance sheet: values at reference builds lv 5 / 10 / 20 (primary 25 / 45 / 90). No value may exceed
   the screen or turn a boss into a free kill.
5. **Art**: pick a sprite pose (unused: attack1, attack2, punch, run_attack, hurt) and an effect from
   `sprite-effect-system.ts`; new icons via the pixel-ui skill.
6. **Build order**: data + unit specs, then resolver mapping, then mechanic in combat-system,
   then VfxEvent + replay, then e2e (solo gesture spec + online visibility), then move-list entry and
   demo clip. One node per commit.
7. **Bots**: give `e2e/support/brain.ts` a branch plan and gesture usage for the class.
8. **Report**: update the tree mock in docs (demo clip via `tools/skill-demos`).

## Checklist per node
- [ ] SkillNode in game-constants (tier, parents, slot, curves, cost, cooldown)
- [ ] Resolver row + fallback, spec green
- [ ] Mechanic; host-side effect for guests via `zombie-effect`
- [ ] VfxEvent emitted + replayed; charge state visible remotely
- [ ] Pixel icon, tree position, move-list demo
- [ ] e2e solo (real key timings) + online visibility, `@skill-<id>` tag

## Pitfalls
- Hold vs auto-swing: a class with no HoldRelease node keeps auto-swing; don't break it.
- Up/Down holds near ladders: ladder wins; test it.
- Never read `this.e.player` in a replay path; take coordinates from the event.

Open questions for you

  4. Stat points. Keep 5 per level allocated by hand, or add a few class presets so skill numbers stay readable?
